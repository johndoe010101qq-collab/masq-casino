## Подготовка папки и ZIP

Следующие команды относятся к **исходному Git-checkout проекта**, с установленными зависимостями и полным набором тестов. После финальной визуальной проверки:

```powershell
npm.cmd test
node scripts/package-miniapp.mjs --build
# Повторная проверка уже построенных файлов без записи:
node scripts/package-miniapp.mjs --check
```

Сборщик требует Node.js, Git CLI, исходный Git-checkout и установленные `spwmini`/Vite. Режим `--build` выполняет финальный Vite build с явно закреплёнными значениями обеих публичных переменных, затем сохраняет `dist/miniapp-build-provenance.json` и готовит папку релиза. Последующая проверка сравнивает конфигурацию, точные хеши входов и сборки; изменение или очистка app ID/пути проверки требует нового `--build`. Обычный `npm run build` не создаёт эту запись происхождения, поэтому для упаковки используется `--build`.

Также проверяются наличие `dist/index.html`, время изменения входов, выбранные файлы Git, стабильность всех хешей во время копирования и реальная HMAC-проверка установленной middleware на синтетических данных. Это локальная проверка происхождения файлов и конфигурации, не подписанное доказательство воспроизводимости сборки. Git может иметь незакоммиченные изменения: в манифесте явно записаны HEAD, статус выбранных файлов и их фактические хеши.

`--check` ничего не записывает и требует уже выполненного `--build`. Обычный запуск без флага упаковывает ранее подтверждённую сборку; `--build` сначала пересобирает `dist`. Упаковка создаёт новую папку `../release-miniapp/indictus-miniapp-<digest>-<timestamp>/` и не удаляет существующие папки релиза. JSON в stdout сообщает абсолютный `releaseFolder` и команду архивации. В папке находятся:

- `webroot/` — полная готовая статическая сборка `dist`;
- `source/` — выбранные клиентские исходники, публичные материалы, package/lock, настройки сборки, этот комплект, [подробный обзор механик и ограничений](MINIAPP_RELEASE_REVIEW.md), черновик заявки, явно перечисленные ниже JSON, пример Nginx и сам сборщик; `.git`, тесты и остальные исторические документы сюда не копируются;
- `README.txt` — назначение папок и ограничения;
- `manifest.json` — размеры и SHA-256 каждого файла, источник сборки, конфигурация идентификации и результаты проверок.

Хеш самого `manifest.json` отдельно возвращается как `manifestSHA256`, чтобы не создавать ссылку файла на собственный хеш. Клиентскую копию `source/` можно собрать после `npm ci`; её package.json сохраняется как исходник, но `npm test` и повторная упаковка требуют полного исходного checkout, где есть тесты и `.git`. Этот отбор не выдаётся за полный архив репозитория.

Явный список review-материалов упаковщика включает оба документа регистрации, `MINIAPP_RELEASE_REVIEW.md`, `SPWORLDS_SUBMISSION_DRAFT.md`, `spw-admin-readiness.json`, `classic-rtp-50-95-receipt.json`, `blackjack-rtp-50-95-holdout.json`, `bonus-purchase-floor-results-v13.json`, `bonus-purchase-floor-provenance-v13.json`, `bonus-purchase-floor-rules-qa-v13.json`. [Пример Nginx](../deploy/nginx-miniapp.conf.example) требует настоящего домена, сертификата и абсолютного пути к `webroot/`. Это статический SPA-хостинг: MIME-типы включены, отсутствующие файлы `/assets/` дают 404, остальные клиентские маршруты используют `index.html`, dotfiles и `/api/` закрыты. Финансовых маршрутов и проверки подписи он не создаёт.

На **HTTP-ответе HTML** должен быть `Content-Security-Policy: frame-ancestors https://spworlds.ru`. Его нельзя заменить meta-тегом. Не добавлять конфликтующий `X-Frame-Options: DENY` или `SAMEORIGIN`. Реальный родитель и вся цепочка iframe должны пройти проверку в SP Worlds.

До передачи проверить адрес без сессии владельца и заголовки, например:

```powershell
curl.exe -I https://ВАШ-ДОМЕН/
curl.exe -I https://ВАШ-ДОМЕН/index.html
curl.exe -I https://ВАШ-ДОМЕН/assets/НЕСУЩЕСТВУЮЩИЙ.js
curl.exe -I https://ВАШ-ДОМЕН/assets/.env
```

Ожидаются доступный HTTPS/200 для страницы, CSP на HTML, 404 для отсутствующего asset и 403/404 для dotfile под `/assets/`. Настоящий домен и сертификаты не поставляются в этом комплекте.

## Подключение известного App ID

Публичный ID `e72e9ddb-1792-4481-ad85-f24e64b24611` предоставлен владельцем для [приложения spm](https://spworlds.ru/spm/apps/e72e9ddb-1792-4481-ad85-f24e64b24611) и записан как `VITE_SPW_APP_ID` в локальную конфигурацию. При подготовке новой согласованной статической версии снова выполнить проверки и `node scripts/package-miniapp.mjs --build`. Сборщик проверяет форму UUID, закрепляет конфигурацию при запуске Vite, фиксирует ID в манифесте и ищет его в собранном JS. Это не проверка владения или одобрения платформой и не разрешение на публикацию.

Выданный один раз токен приложения сохранить только в серверном секрет-хранилище. **Не отправлять токен в чат**, не записывать в исходники, этот JSON, `VITE_*` или клиентский bundle. Токен приложения и ID/токен банковской карты — разные учётные данные; банковские данные этому DEMO не нужны.

Для статического DEMO оставлять `VITE_SPW_VALIDATE_URL` пустым. Непустой путь включать только после развёртывания работающего same-origin endpoint. В опубликованной версии backend отсутствует; путь не доказывает его работу. Старый контракт `validateUser` POST-ит непосредственно `sdk.user` и ожидает текст строго `1`/`0`, а не JSON `{valid:true}`. Новая локальная панель использует отдельный `/api/auth/spw` с серверной сессией/узкими возможностями; включается через `VITE_MASQ_SERVER_ADMIN` с соответствующим сервером по [SERVER_ADMIN.md](SERVER_ADMIN.md). Ни одна из этих проверок не создаёт финансовый журнал.

`server/spw-validate.js` нельзя называть производственным сервером: это отдельный пример без установленного Express, точки запуска, серверной сессии и финансового журнала. Слово `production` в описании `dist` означает оптимизированную клиентскую сборку; оно не подтверждает регистрацию, действующий backend или возможность операций с настоящими АР.

SDK отправляет `{type:'init', payload:appId}` родителю. Ответ — `initResponse` с профилем или `initError` со строкой; `ready` генерируется локально SDK, отдельного outgoing-ready нет. Адаптер проверяет `event.source === window.parent` и origin `https://spworlds.ru`.

В npm1.2.0 тип профиля содержит четыре поля; официальный репозиторий позднее добавил `timestamp`, `roles`, `isAdmin` без смены версии. Текущий адаптер требует расширенный семиполевой формат. При первом запуске проверить настоящее сообщение; не предполагать совместимость только по номеру пакета. Единицы `timestamp` не определены проверенными первичными источниками. `checkUser` проверяет HMAC, но принимает корректно подписанные старые/будущие timestamps. Локальная административная сессия требует явно подтверждённую единицу времени, принимает подпись не старше пяти минут с допуском будущего времени 30 секунд и истекает через 15 минут. Повтор обмена той же свежей подписи возможен в этом окне; полная защита от повторного использования не заявляется. Без серверных параметров вход закрыт; в опубликованной версии административной сессии нет.

## Передача на модерацию

Репозиторий исходников — публичный GitHub; развёртывание обновлённого сайта и передача заявки на модерацию пока отложены. Заявка не отправлена; исходники доступны для чтения без приглашения. Перед продолжением подтвердить владение созданным приложением и поля формы, настроить секреты приватно, подготовить конкретную сборку, затем проверить HTTP CSP и **настоящий iframe**. Статическое размещение и развёртывание серверной панели — отдельные действия. Проверить имя, права админки, все девять игр, мобильный размер, правила шансов и отсутствие неподключённых финансовых запросов. Старые измерения остаются историческими; цели RTP не гарантируют результатов.

Приложить описание DEMO, список используемых полей профиля и ограничения серверной проверки. Допустимость игр и условия публикации определяет SP Worlds; комплект не утверждает одобрение, соответствие неизвестным правилам площадки или безопасность настоящих денег.

К каждой передаваемой версии приложить ссылку на frontend-репозиторий, состояние backend, номер версии/commit, `contentDigest` и `manifestSHA256`, краткое описание изменений и актуальный обзор механик. Полученное согласование фиксируется отдельно вместе с версией. Последующее обновление не считается автоматически согласованным по одобрению предыдущего пакета.
