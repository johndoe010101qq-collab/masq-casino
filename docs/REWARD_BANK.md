# Банк наград MASQ

`server/reward-bank.mjs` — отдельный серверный учёт дополнительных наград. Он не меняет RNG, символы, RTP или выплаты игровых движков. Награда записывается отдельным обязательством перед участником; она не выдаётся за выигрышную комбинацию слота.

Сейчас модуль не подключён к доверенному игровому серверу, клиентскому `HallSession`, административному финансовому HTTP-методу или платёжному API. Созданное обязательство имеет статус `reserved-uncredited`: баланс игрока и настоящие АР этим модулем не изменяются. Наличие кода и настройки не означает, что эта механика уже работает на Cloudflare Pages.

Существующий административный сервер предоставляет владельцу чтение состояния и изменение политики через `GET/PUT /api/admin/rewards`. Эти методы не принимают сыгранные раунды, не запускают раздачу и не начисляют деньги. В этом сервере доверенный адаптер ставок не подключён, поэтому `authorityConfigured` остаётся `false`.

## Откуда берётся банк

В банк попадает только маржа **завершённых доверенных денежных ставок**: полное списание ставки минус её полная выплата. Депозит, клиентское сообщение о проигрыше, предварительный результат, демонстрационные фишки и сами награды не являются прибылью казино.

Настройки по умолчанию:

- доля маржи для наград — 50%;
- минимальный нераспределённый банк для новой раздачи — 5000 АР (`500000` целых сотых);
- награда одному участнику — от ×10 до ×30 его последней записанной **базовой** ставки в данной серверной группе;
- максимум пять разных получателей в одной раздаче.

При постоянной доле 50% накопленная положительная маржа 10 000 АР создаёт право на 5000 АР наград. Из права на награды вычитаются **все ранее распределённые обязательства**, поэтому та же прибыль не используется второй раз. Проигрыш казино уменьшает оставшийся нераспределённый банк. Если новые убытки снизили право ниже уже начисленных обязательств, обязательства сохраняются, появляется `entitlementShortfallCents`, а новые награды блокируются до восстановления бюджета.

Формула: `право = floor(max(0, все завершённые ставки − все завершённые выплаты) × текущая доля / 100)`, `доступный банк = max(0, право − уже начисленные награды)`. Изменение доли пересчитывает невыданную часть по всей накопленной чистой марже. Уже созданные обязательства сохраняются. Выключение доли во время убытка не сохраняет старый пул: после возвращения прежней доли расчёт всё равно включает убыток.

Все суммы хранятся в безопасных целых сотых АР. Половинки сотой накапливаются до итогового округления вниз, а не теряются на каждом раунде. SQLite использует WAL и `synchronous=FULL`. Запись раунда, событие истории и изменение счётчиков атомарны; запись раздачи, обязательств всех получателей и её истории также атомарна.

## Кому и сколько

`sessionKey` задаётся доверенным серверным учётом и определяет группу участников. Подходят уникальные `accountId`, у которых в этой группе уже есть записанный завершённый раунд. Последняя базовая ставка определяется по наибольшему доверенному `settledSequence`, а не времени загрузки записи в банк. Поздняя загрузка старого раунда не возвращает старую базу и не создаёт новый повод для раздачи. Полная стоимость покупки бонуса не подставляется вместо базовой ставки.

Перед выбором получателя проверяется, помещается ли хотя бы ×10 его базовой ставки в текущий остаток. Среди подходящих по бюджету участников выбор равновероятен. После выбора выбирается равновероятный целый множитель от минимального до меньшего из максимального и доступного `floor(остаток / базовая ставка)`. Получатель исключается из дальнейшего выбора внутри этой раздачи. Следующий выбор снова учитывает оставшийся банк.

Для базы 5 АР награда составляет 50–150 АР. Покупка бонуса за 250 АР при той же базе 5 АР не превращает её в награду 2500–7500 АР. Если база 1000 АР, а банк 5000 АР, минимум ×10 не помещается: участник пропускается, сумма не урезается до ×5. Остаток банка переносится на будущие раздачи; тратить все 5000 АР за один раз не требуется.

Поэтому равный шанс относится к текущему набору участников, чья минимальная награда помещается в банк. Участники с более высокой базой могут ждать увеличения банка. Это финансовое ограничение опубликованной механики, а не персональная коррекция игрового исхода.

Повтор того же `eventId` возвращает записанную раздачу без нового RNG и обязательств. После успешной раздачи другой `eventId` без нового наибольшего `settledSequence` в той же группе не создаёт новые награды. Пропуски из-за порога, выключенной доли или отсутствия доступного получателя записываются в историю, но не лишают ожидающих участников будущей раздачи, когда банк пополнится или политика изменится. Новый доверенный раунд позволяет новую проверку после успешной раздачи; после небольшой раздачи при банке ровно на пороге остаток оказывается ниже порога.

## Контракт будущего сервера

Конструктор:

```js
const bank = createRewardBank({
  databasePath: '/private/path/rewards.sqlite',
  readSettledRound: id => authoritativeWagerLedger.readFinalMoneyRound(id),
  // randomInt: optional unbiased synchronous server RNG; defaults to node:crypto.
});
```

`readSettledRound(id)` должен быть синхронным адаптером **серверного** окончательного журнала ставок. Для завершённого раунда он возвращает строго:

```js
{ id, accountId, sessionKey, settledSequence, baseStakeCents, stakeCents, payoutCents }
```

`stakeCents` — полная плата входа, `baseStakeCents` — исходная ставка. `settledSequence` — положительное безопасное целое число из окончательного журнала, уникальное для каждого раунда и возрастающее в истинном порядке завершения ставок. Оно не создаётся браузером и не заменяется локальным номером импорта. Для отсутствующего или незавершённого раунда возвращается `null`. Происхождение JSON само по себе не подтверждает доверие: этот адаптер нельзя реализовывать через клиентский баланс, переданный HTTP-объект или неподписанное сообщение. После окончательного завершения раунд и идентификаторы неизменны; повтор ID с другими суммами, участником, группой, порядком или базой отклоняется. Повтор последовательности с другим ID также отклоняется.

Серверный обработчик сначала вызывает `recordSettledRound(id)`, затем может вызвать `drawRewards(eventId, sessionKey)`. Группа для вызова должна поступать из того же авторитетного журнала. Сам модуль не решает, когда запускать обработчик, не создаёт HTTP-методы и не принимает пользовательские команды на награждение.

Без адаптера `authorityConfigured` равен `false`. Чтение банка и настройка политики доступны, а накопление, раздача и создание денежных обязательств отклоняются с `AUTHORITY_UNCONFIGURED`. Подключение авторитетного журнала — отдельная требуемая работа, не скрытый обход входа.

Доступные методы:

- `snapshot()` / `read()` — настройки, версии, чистая маржа, право на награды, доступный банк, созданные обязательства и дефицит после убытков;
- `recordSettledRound(id)` — идемпотентная запись доверенного завершённого раунда;
- `drawRewards(eventId, sessionKey)` — атомарный выбор нескольких участников, запись RNG-билетов для проверки и отдельных обязательств;
- `configure(policy, { actorId, reason, expectedRevision })` — полная политика, ожидаемая версия настроек и журнал причины; `actorId` должен поступать из проверенной серверной авторизации;
- `history({ limit, cursor })`, `liabilities({ accountId, limit, cursor })`, `eligibleAccounts({ limit, cursor })` — ограниченные страницы истории и обязательств;
- `close()` — закрытие базы.

Метода произвольного назначения получателей и сумм наружу нет: записать новые обязательства можно только через публичную политику `drawRewards`. Внутренний атомарный обработчик проверяет и сохраняет рассчитанные назначения одной транзакцией.

Политика содержит только `returnPercent`, `minimumBankCents`, `minStakeMultiple`, `maxStakeMultiple`, `maxWinners`. Доля — целые 0–100%, порог — положительные целые сотые, множители — целые 1–100 с минимумом не больше максимума, получатели — целые 1–100. Нулевая доля запрещает новые случайные награды. Настройки и аудит сохраняются при перезапуске.

Результат `drawRewards` не является подтверждением платежа. Для настоящего начисления потребуется отдельный атомарный серверный кошелёк с идемпотентным ключом каждой награды и согласованной платёжной интеграцией. В текущем модуле нет метода, который отмечает обязательство выплаченным без такого учёта.

## Проверка

`node tests/reward-bank-checks.mjs` проверяет накопление, обычные выплаты и убытки, повторы раундов и раздач, сохранение после перезапуска, базовую ставку покупки бонуса, разные группы, доступный множитель, уникальность получателей, отсутствие перерасхода, ошибочные RNG-билеты, откат частичной раздачи и настроек при ошибке SQLite. Используется синтетический серверный журнал и временная база. Настоящие платежи, токены и внешний хостинг в проверке не участвуют.
